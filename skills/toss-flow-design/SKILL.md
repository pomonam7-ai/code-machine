# Toss Flow Design

업종에 맞는 모바일 앱·웹 동선을 설계하거나 구현한다. 토스 실앱에서 관찰한 탐색·목록·입력 패턴을 사용자의 제품에 맞게 바꾼다. 기존 브랜드, 요구사항, 플랫폼 관례를 우선한다.

## 적용 범위

- 새 서비스: 핵심 과업과 정보 구조를 정한 뒤 화면·상태·구현으로 연결한다.
- 기존 서비스: 요청된 동선의 병목을 개선한다. 관계없는 화면을 다시 만들지 않는다.
- 분석 요청: 화면 흐름과 근거를 전달한다. 분석만 요청했으면 코드 수정·배포로 확대하지 않는다.
- 구현 요청: 설계 설명만으로 끝내지 말고 해당 환경의 개발·검증 절차로 실제 동작을 구현한다.

이 스킬은 특정 프레임워크, Mobile MCP, 외부 계정, API 키를 필수로 하지 않는다. 실기기 조사는 요청되었거나 필요할 때만 수행한다. 별도 제작 도구를 사용하는 경우 해당 도구의 워크플로를 따른다.

## 1. 제품의 과업을 먼저 정하기

대화·기존 화면·코드를 바탕으로 다음을 짧게 정리한다. 결정 가능한 내용은 합리적으로 가정하고 진행하며, 결과를 바꾸는 정보만 질문한다.

- 사용자와 사용 상황: 예를 들어 이동 중 한 손 사용, 처음 방문, 반복 업무.
- 핵심 대상: 고객, 예약, 문서, 상품, 학습 과정 등.
- 성공 상태: 저장, 요청 접수, 예약 확정, 발송 확인 등 실제 의미.
- 주된 사용 방식: 빠른 실행 / 비교·탐색 / 기록·모니터링.
- 실제 연결: 로컬 저장, 서버 저장, 외부 앱 열기, 백그라운드 처리 여부.

과업에 맞게 정보 밀도를 고른다. 업무형은 대상과 다음 행동을, 탐색형은 검색·비교 정보를, 모니터링형은 상태와 예외를 먼저 보여준다. 탐색이 목적인 화면을 억지로 선형 단계로 바꾸지 않는다.

## 2. 적합한 흐름 고르기

전체 서비스의 모든 기능에 같은 플로우를 적용하지 않는다. 필요한 패턴만 고른다.

| 사용자 과업 | 적합한 기본 흐름 | 중요한 판단 |
| --- | --- | --- |
| 이미 아는 일 빠르게 처리 | 요약·대상 목록 → 대상 선택 → 핵심 행동 → 결과 | 목록에서 바로 실행해도 맥락이 충분한가? |
| 처음 대상이나 서비스 찾기 | 검색·카테고리 → 결과 비교 → 상세 → 행동 | 추천 검색어·결과 분류는 실제로 탐색을 줄이는가? |
| 정보 입력·제출 | 목적·대상 → 필요한 입력 → 필요 시 검토 → 실행 → 상태 | 서로 의존하는 입력과 실수 비용이 큰 단계를 구분했는가? |
| 반복·중단된 작업 재개 | 최근 작업·진행 중 → 이전 상태 복원 → 이어서 수행 | 대상·입력·선택한 탭·목록 위치를 복원할 필요가 있는가? |
| 사용 환경 관리 | 설정 진입 → 관련 항목 묶음 → 상세 변경 → 반영 피드백 | 핵심 업무 입력에서 반복 설정을 제거했는가? |

‘한 화면 한 질문’은 인지적으로 하나의 결정에 집중한다는 뜻이다. 이름·연락처 같은 짧고 밀접한 필드를 여러 페이지로 불필요하게 나누지 않는다. 검토 화면·확인 모달도 실수 비용에 비례해 사용한다.

메인 탐색은 서비스의 동등한 상위 영역에 사용하고, 세부 작업은 해당 맥락 안에서 진입·복귀하게 한다. 하단 탭 5개나 ‘전체’ 메뉴를 의무적으로 만들지 않는다. 모바일에서는 하단 탐색, 넓은 웹에서는 사이드바 등으로 바꿔도 과업의 이름과 의미는 유지한다.

## 3. 화면과 상태를 함께 설계하기

복잡도에 맞는 간단한 흐름도 또는 아래 표를 작성한다. 작은 변경은 해당 구간만 다룬다.

| 화면 | 사용자가 답할 질문 | 필요한 정보 | 주요 행동 | 다음 상태·복귀 |
| --- | --- | --- | --- | --- |

다음 원칙으로 구체화한다.

- **요약 + 다음 행동:** 대상 행에 이름·현재 상태·다음 할 일을 함께 둔다. 행의 상세 이동과 별도 실행 버튼의 클릭 영역·의미를 구분한다.
- **반복 작업 재진입:** 최근 사용·진행 중·즐겨찾기는 반복 사용에 이득이 있을 때 넣는다. 가짜 이력이나 임의의 실적 수치를 만들지 않는다.
- **점진적 입력:** 핵심 필드를 먼저 받고 선택 정보는 필요할 때 펼친다. 비용·중요 조건·필수 동의는 숨기지 않는다.
- **명확한 피드백:** 버튼의 동사는 실제 수행과 일치하게 한다. 복사·공유 창 열림·접수·처리 완료를 각각 다른 상태로 취급한다.
- **돌아갈 수 있는 작업:** 뒤로가기로 입력·선택이 사라지지 않게 한다. 오래된 초안을 복구하면 대상과 변경 사항을 다시 확인할 수 있게 한다.

해당 기능에 필요한 첫 사용·빈 목록·검색 결과 없음·검증 오류·저장 실패·처리 중·완료 상태를 포함한다. 서버나 외부 작업이 있다면 중복 실행, 재시도, 지연·미확인 결과도 구분한다. 연결되지 않은 기능을 성공한 것처럼 표시하지 않는다.

## 4. UI와 문구에 반영하기

브랜드가 정해져 있으면 그 색상·서체·컴포넌트 체계를 유지한다. 토스와 비슷한 스타일을 요청한 경우 밝은 중립 배경, 관련 정보를 묶은 카드, 넓은 행 높이, 분명한 제목·본문·보조 설명 위계를 출발점으로 삼는다. 예시 색상이나 간격을 토스 공식 토큰이라고 설명하지 않는다.

- 목록 이동에는 제목·설명·화살표, 별도 행동에는 명확한 버튼을 사용한다. 모든 요소를 강한 브랜드색으로 칠하지 않는다.
- 한 결정에서 가장 중요한 행동의 위계를 분명하게 한다. 서로 독립적인 목록 행에 각각 행동이 있는 것은 허용한다.
- 사용자의 질문으로 제목을 쓸 수 있다. 예: ‘언제 방문할까요?’, ‘어떤 문서를 만들까요?’ 정확성이 필요한 상세 화면은 명사형 제목도 적합하다.
- 버튼은 ‘확인’ 대신 맥락에 맞는 ‘예약 요청하기’, ‘초안 저장’, ‘복사하기’처럼 결과를 예측하게 한다.
- 상태는 색상과 함께 텍스트로 표시하고, 아이콘 버튼에 이름을 제공한다. 키보드·확대·긴 텍스트에서도 조작할 수 있게 한다.
- 모바일 터치 영역은 보통 44~48 CSS px 이상을 출발점으로 삼고 플랫폼 기준을 따른다. 키보드·안전 영역·고정 버튼이 입력을 가리지 않게 한다.
- 로딩·전환 모션은 상태 이해에 도움이 되는 곳에 짧게 사용하고 모션 감소 설정을 반영한다.

로고·화면 캡처·캐릭터·문구를 무단 복제한 템플릿으로 만들지 않는다. 구조적 원칙을 사용자의 콘텐츠와 브랜드로 구현한다.

## 5. 구현과 검증

설계 요청이면 판단 근거와 동선을 전달한다. 구현 요청이면 기존 기술 스택을 사용하고 실제 연결 범위 안에서 동작을 완성한다.

요청 범위에서 대표 경로 하나를 끝까지 확인한다. 입력 → 오류 교정 → 실행 → 결과 → 목록 재진입이 해당한다면 모두 확인한다. 작업 특성에 따라 뒤로가기 복원, 필터·탭 유지, 빈 상태, 저장 실패, 반복 누름, 모바일 키보드가 필요한 검증을 고른다. 실행·발송·결제 상태가 섞이는 기능은 그 경계를 특히 확인한다.

결과를 전달할 때 다음을 분명하게 한다.

- 사용자가 실제로 할 수 있게 된 일.
- 줄어든 탐색·입력 또는 더 명확해진 상태.
- 직접 검증한 범위와 외부 연동·실기기 검증의 한계.

## 필요한 경우에만 읽는 참고 자료

- 토스에서 직접 확인한 범위와 근거가 필요하면 [관찰 근거](references/observations.md)를 읽는다. 확인하지 않은 송금 완료나 보안 제한 구간을 실측한 동선으로 주장하지 않는다.
- 업종별 적용이 어려우면 [분야별 적용 예시](references/domain-mapping.md)를 읽고 대상·행동·상태를 치환한다. 예시 전체를 제품 요구사항으로 추가하지 않는다.
